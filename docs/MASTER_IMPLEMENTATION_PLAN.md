A live dry run over 2 real accounts verified the full chain end-to-end: Apify fetch → `PostLoader` → media processing to B2 → run summary to Discord (`#clubsync-log`) → healthchecks.io ping (finished). Remaining: Phase 2 (dedup), Phase 3 (extraction), the Phase 4 circuit breaker, Phase 5, and deployment to the E5440.

> **Stage-order correction (September 21, 2026):** this plan originally read `scraped → media_processed → deduped → extracted`. Dedup runs *after* extraction (it needs the extracted event date and confidence), so the order is now **`scraped → media_processed → extracted → deduped`**. `deduped` is the terminal stage. Every occurrence below has been updated, and the companion docs now own the details. `REPO_STATE.md` documents the as-built differences (e.g. the `events` table was marked done here but never created; it is now pulled into Phase 2).

## 1. Goal

Ingest event posts from ~41 Instagram accounts, extract structured event data (date, venue, etc.) via vision LLM, dedupe reposts, and surface confirmed events — as a solo-maintained side project, self-hosted, near-zero monthly cost, correctness prioritized over speed.

**v1 scope:** Instagram only. Everything else (Telegram/Threads/manual submission, cross-account dedup, notification-trigger phone layer) is explicitly deferred.

## 2. Finalized Architecture Decisions

| Component | Decision | Replaces (original doc) |
|---|---|---|
| Media storage | Backblaze B2 (S3-compatible), via a thin `ObjectStore` wrapper (`put`/`get_url`) | Self-hosted MinIO on the E5440 |
| Media processing (resize/compress) | Folded into the same ingestion pass, synchronous, run immediately after `PostLoader` persists the `Post` row (not the adapter — `PostAdapter` never touches the DB) — avoids any queueing delay before Instagram's signed `displayUrl` expires. Each image resized to 1080px max width and re-encoded as WebP via `ruby-vips` (confirmed a valid Gemini vision input MIME type). Uploaded via the existing `ObjectStore`, now passing `content_type: "image/webp"` explicitly since it otherwise defaults to JPEG. Per-image metadata (`b2_key`, dimensions, byte size, ordinal position, a nullable `dhash` for Phase 2) lands in a new `images` table — one row per image, so a `Sidecar` post's images (Instagram caps carousels at 10, so no extra cap needed) are properly modeled rather than crammed into an array column. Only the processed bytes are kept — no original retained, same "Instagram is the source of truth" logic already used to justify skipping Postgres backups. Note: `source_url` (the permalink) and the actual expiring image URL are different fields — the latter is `raw_payload["displayUrl"]` (`Image` posts) or each `raw_payload["childPosts"][i]["displayUrl"]` (`Sidecar` posts); nothing reads these yet | New — Phase 1 checklist item was underspecified (no storage shape, no failure semantics) |
| Media processing — atomicity & retry | All of a post's images are fetched/resized/uploaded inside one DB transaction: either every `images` row for that post gets written, or none do — so there's no per-image status column, only a per-post one (see Post state model below). On any failure (expired URL, corrupt file, network error), the post's `stage` simply doesn't advance past its last completed value, and `last_error`/`stage_failed_at` record why; `raw_payload` is still refreshed to whatever was just scraped. Retry is passive, not a dedicated job: the same account gets re-scraped every 2 days regardless, so a stalled post picked up again in a later run (with a fresh, unexpired `displayUrl`) simply resumes from its current stage; a post whose `stage` is already `deduped` (fully processed, terminal) is left alone. Gets resilience against transient failures for the cost of one stage check, no retry-count/backoff machinery | New — resolves "what retries a failed post?", previously unspecified |
| **Post state model** | `posts.status` (single enum) replaced by `stage` (`scraped → media_processed → extracted → deduped`, tracks the last pipeline stage that completed successfully; `deduped` is the terminal stage) + `is_event` (nullable boolean — `nil` until `stage == extracted`, then `true`/`false`) + `last_error`/`stage_failed_at` (both cleared the next time that stage succeeds). No retry-count/attempts table: a stalled stage is just re-attempted from scratch on the next cron pass, since each stage's operation (resize/upload, dHash, LLM call) is treated as idempotent. **Reorder consequence:** "fully processed" is now `deduped`, so `PostLoader`'s skip guard keys off `post.deduped?` (was `post.extracted?`) — see the dedup plan §6 | Replaces the originally-planned five-value `status` enum (`pending`/`done`/`needs_review`/`rejected`/`failed`), which conflated pipeline progress with business outcome across four different layers using overlapping terms (`pending` meant different things at the Adapter vs. media-processing layer, etc.) |
| "Rejected" concept | Not a stored value anywhere. Structural invalidity is inferred, not recorded: missing/blank shortcode → `PostAdapter` returns a fatal result, `PostLoader` never creates a row; unsupported `post_type` (e.g. `"Video"`) → row is still created (raw payload preserved) but its `stage` never advances past `scraped`. Anything wanting "real" posts filters `post_type IN ('Image', 'Sidecar')` directly, rather than reading a status | Replaces the `rejected` status value |
| "Needs review" concept | Not a stored post-level column. **Resolved (2026-09-21):** per-field extraction confidence is stored on `events.per_field_confidence` (table created in Phase 2), so "needs review" is a query — `events WHERE superseded_by_event_id IS NULL AND per_field_confidence->'<field>' < threshold` — not a status | Replaces the `needs_review` status value. The confidence-storage location (previously flagged unresolved) is settled |
| Adapter / Loader split | `PostAdapter` (built): pure mapping of one raw Apify hash → canonical attributes + validation. Never touches the DB, never decides `stage`/`is_event`. Returns a `Result` (`valid?` / `errors` / `fatal?`) — `fatal` only for missing/blank shortcode. `PostLoader` (to build, Phase 1): owns all `Post` DB writes and the stage-routing logic — see Phase 1 checklist for its exact behavior | New — makes explicit a division of responsibility the original doc left implicit |
| **Ingestion orchestration split** | `AccountPipeline` (per-account: fetch → `PostAdapter` → `PostLoader` → `MediaProcessor`, returns a `Result` with `success?`/`errors`/`posts_scraped`, narrow rescue on anticipated Apify exceptions only) + `IngestionRunner` (per-run: loops accounts, tallies `Result`s, outer `rescue`/`ensure`, calls the notifiers). The rake task itself is a one-line delegation to `IngestionRunner.call`. Full spec in `docs/DATA_INGESTION_IMPLEMENTATION_PLAN.md` | New — the original plan had this logic sketched directly inside the rake task; split out once it became clear that block was carrying two responsibilities (per-account work vs. run-level reporting) and wasn't unit-testable as written |
| **Account source of truth** | New `accounts` table (`Account` model, `handle` unique) instead of a constant/YAML list — the 41 handles are hand-maintained (`db/seeds.rb`, not a data migration, since `db:schema:load` won't replay migration-seeded data on a fresh box), no admin UI. Built as a real table now rather than deferred because Phase 4's circuit breaker needs per-account state that persists between runs, unlike stage progression there's no idempotent substitute for that memory, and it avoids a second table-creation migration later. `posts.account` stays an untouched plain string — no FK | New — the docs had `Account.all` without any model behind it |
| Background jobs / workers | None, anywhere in this pipeline. Everything is cron-triggered via a rake task, never triggered by a user request, so there's no request/response cycle to protect (unlike the CSV-import/email pattern in the other Rails project). The one legitimate future case — retry-on-demand for a single stalled post — isn't needed for v1 | New — confirms Sidekiq/Redis isn't warranted here |
| Test factories | `factory_bot_rails` + `faker`. Factory defaults use Faker for incidental filler values (usernames, captions, counts, timestamps); literal values are reserved only for what a given test specifically asserts on (`post_type`, deliberately-invalid trait overrides like `:bad_timestamp`/`:blank_shortcode`). Tests assert against the built factory instance's own fields, never against hardcoded literals that happen to match factory defaults. `FactoryBot.lint` is only meaningful for real AR-backed factories (e.g. `Post`/`Image` for `PostLoader` tests) — the `class: Hash, skip_create` Apify-payload factories bypass the DB entirely, so a lint test on those wouldn't catch anything real | New — corrects the initial `PostAdapter` test factories, which used hardcoded literals throughout |
| "Prune" (compress/prune before B2) | Descoped for v1. B2 doesn't auto-delete anything when the 10GB free tier is exceeded — it either bills (~$0.007/GB/month) or, with a hard cap and no payment method, rejects new uploads (a pipeline failure, not silent data loss). At WebP/1080px volume across 41 accounts every 2 days, reaching that threshold is far off. Revisit only if B2 usage becomes a real line item — options then are Backblaze's basic lifecycle (hide/delete) rules, or app-level deletion of images tied to past events | Was assumed to be a needed mechanic; turned out not to be |
| Compute / orchestration | Self-hosted on the revived Dell Latitude E5440, cron-triggered, containerized via Docker + Compose (`app` + `db` services). The same box also hosts ProPro's *staging* environment (separate containers, separate Postgres instance) — the two workloads don't overlap in a way that stresses the hardware (ClubSync's cron job is bursty and network-bound; ProPro staging traffic is light), confirmed by intent to spot-check with `docker stats`/`htop` under real concurrent load. Heroku (GitHub Student Pack credit) was considered again but reserved for ProPro *production* instead, since that has real coordinator/lecturer/student users who benefit more from managed uptime — staging carries a lower uptime bar so co-locating it here is an accepted trade-off | Was briefly considered for Heroku; reverted — see Section 4 |
| Remote access / management | Tailscale (SSH into the E5440 from anywhere, no port-forwarding); lid-close sleep already disabled. This is for your own admin/SSH access — separate from the public-facing path below, which reaches the app over the open internet, not the tailnet | N/A — new since last revision |
| Database | Postgres, self-hosted on the E5440, in its own container — kept separate from ProPro's Postgres instance since ProPro is a real project with a real team. Backups are explicitly out of scope for v1: Instagram is the source of truth for the underlying content, so losing this DB costs a re-scrape + re-extraction pass (time, some free-tier API calls), not permanent data loss — a materially different risk than ProPro, which holds data with no external copy | Was an open gap ("has to be backed up manually"); resolved as intentionally deferred, not forgotten |
| Secrets | `.env`, git-ignored, `chmod 600`, transferred once via `scp` over the Tailscale IP — never committed. `APIFY_API_TOKEN` holds the raw token string only (`apify_api_...`) — not a full run-sync URL with the token embedded as a query param. Sent via `Authorization: Bearer` header, never as a URL parameter | Rails encrypted credentials (considered, dropped as unnecessary overhead for a solo project) |
| Health monitoring delivery | `IngestionRunner` pings healthchecks.io (`/start`, `/fail`, success) and posts a run summary to Discord's `#clubsync-log` on every run, regardless of outcome; healthchecks.io's own missed-ping alerts route separately to `#clubsync-alerts` via its native Discord integration. Full spec in `docs/HEALTH_MONITORING_PLAN.md` | A Grafana/Loki/VictoriaMetrics stack was considered and deferred — too heavy a resource sink for the E5440 relative to what one cron job's heartbeat needs |
| App framework | Ruby on Rails — single app, single language | N/A |
| Perceptual hashing (dedup) | Hand-rolled dHash in Ruby, using `ruby-vips` (already needed for the 1080px resize step) | Python `imagehash` library |
| Extraction LLM | Google Gemini (3.1 Flash-Lite or 3 Flash), via Google AI Studio free tier | "Undecided vision-capable LLM" |
| Embeddings (caption-similarity fallback) | Google `gemini-embedding-2`, same free-tier account (updated 2026-09-21 — supersedes `gemini-embedding-001`, see the dedup plan §1) | "Undecided" embedding API |
| Scheduling | OS cron on the E5440, managed via the `whenever` gem, every 2 days. Since the app runs in a container, `whenever` writes a host-level crontab entry that calls `docker compose exec app bin/rails clubsync:ingest` rather than running a scheduler inside the container. "Staggering across accounts" is no longer a separate scheduling concern — `AccountPipeline` processes accounts sequentially within the one cron-triggered run, which staggers the downstream load (image processing, Gemini calls) as a side effect, with no offset-schedule logic needed | Heroku Scheduler (considered, not used); also replaces the earlier assumption that staggering required per-account cron offsets |
| Scraping | Apify Instagram Post Scraper (`apify/instagram-post-scraper` — not the general `apify/instagram-scraper`) | Unchanged |
| Public exposure | **Resolved: in v1 scope.** Cloudflare Tunnel (`cloudflared`) on the E5440 fronts a public-facing surface — anyone can browse confirmed events and report one as wrong, no login, no reaching out to the maintainer | Was the open decision below; previously assumed Tailscale-only |
| Admin/review surface protection | Now that part of the app is internet-facing via the same Rails process, "nobody but me is on this tailnet" no longer protects the review queue. Gated in-app with HTTP Basic Auth (credentials via `.env`), independent of which network path a request came in on | N/A — new requirement created by adding public exposure |
| Public write abuse protection | Rack::Attack, IP-based rate limiting on the flag endpoint and public routes generally, since the flag action is now an unauthenticated public write | N/A — new |

Media storage stays unaffected by any of this — B2 is already off-box, so there's no self-hosted bucket to expose either way.

**⚑ Resolved: `is_event` stays as a boolean column on `posts`.** The LLM sets it based on its confidence and decision threshold during extraction. "Is this an event" is a per-post business judgment, not derivable from whether an `events` row exists (an `events` row holds structured field data for confirmed events; a post can be classified as non-event without one).

## 6. Implementation Phases

**Phase 1 — Foundation**
- [x] Rails app scaffold
- [x] B2 `ObjectStore` wrapper (`put`/`get_url`) — built and tested
- [x] Postgres schema/migration: `posts` (shortcode unique key, account, post_type, caption, source_url, posted_at, `raw_payload` jsonb, `stage` enum, `is_event` boolean, `last_error`, `stage_failed_at`) — *built and tightened to match the Post state model above.* **The `events` table was originally marked done here but was never created** (no model/migration exists; confirmed 2026-09-21 — see `REPO_STATE.md`). It is now pulled **forward into Phase 2** (see below), where the long-open "where does per-field confidence live / events vs. `is_event` reconciliation" item is resolved: confidence lives on the `events` row itself (`per_field_confidence`), and `is_event` (a boolean on `posts`) stays the per-post business classification independent of whether an `events` row exists
- [x] Apify integration + secrets (`.env`, git-ignored, `chmod 600`) — follow-up fix landed: client targets `apify/instagram-post-scraper` via `POST .../run-sync-get-dataset-items` with input `{"username": [handle], "resultsLimit": 10}`; the raw token (`APIFY_API_TOKEN`) is sent as `Authorization: Bearer`, never as a URL param. Exposed as distinct exception classes (`TimeoutError`, `RateLimitedError`, generic). Verified against real Apify in the September 2026 dry run
- [x] `PostAdapter`: raw JSON → canonical attributes, validated; never touches the DB, never decides `stage`/`is_event` — that's `PostLoader`'s job. Returns a `Result` (`valid?` / `errors` / `fatal?`); `fatal` only for missing/blank shortcode. `raw_payload` captured in every non-fatal result regardless of validation outcome
- [x] Migration: make `account`, `post_type`, `source_url`, `posted_at` nullable on `posts` — lets a structurally-invalid post (e.g. unsupported `post_type`) still get a row via `PostLoader` instead of being dropped; that row's `stage` simply never advances past `scraped`
- [X] `PostLoader` service — owns all `Post` writes during ingestion, nothing else. **Narrowed scope vs. the original plan (see the `PostLoader` spec §1):** it does *not* advance `stage` and never touches `is_event` / `last_error` / `stage_failed_at`. `stage` only moves when the corresponding stage-service succeeds (`MediaProcessor` already self-guards via `post.scraped?`), and error state belongs to those services — clearing it "on the next successful run of *that* stage," not on re-scrape. Full behavior table in the `PostLoader` spec §3:
  - Shortcode not found → create row, `stage: scraped`
  - Shortcode found, `stage == deduped` (terminal) → skip entirely, don't touch the row
  - Adapter fatal result (no shortcode) → no row created
  - Result reports `created` / `refreshed` / `skipped` / `no_row` — `refreshed` replaces the old `advanced`/`stalled` pairing (Loader refreshes row data, it can't "stall" a pipeline stage; a real failure here is a bug that raises). Deliberately **no** `retried` outcome, that was leftover from the dropped Instaloader-primary/Apify-fallback design
- [X] Media processing (folded into the same ingestion pass, right after `PostLoader` persists the `Post` row):
  - [X] Migration: new `images` table (`post_id` FK, `position`, `b2_key`, `content_type`, `width`, `height`, `byte_size`, nullable `dhash`), unique index on `[post_id, position]` — no per-image status column; decided against it since media processing is one atomic transaction per post (revisit only if a real per-image need, e.g. dedup, shows up)
  - [X] For each post's image(s) — `raw_payload["displayUrl"]` (`Image`) or each `raw_payload["childPosts"][i]["displayUrl"]` (`Sidecar`) — fetch, resize to 1080px max width, re-encode as WebP via `ruby-vips`
  - [X] Upload each via `ObjectStore#put`, passing `content_type: "image/webp"` explicitly
  - [X] Wrap all of one post's image writes in a single transaction: all `images` rows or none
  - [X] On success: `images` rows persisted, `stage` advances to `media_processed`. On failure: `stage` stays put, `last_error`/`stage_failed_at` set, `raw_payload` still refreshed to the latest scrape
  - [x] Setup Factory bot for tests to reduce redundancy + protect against upstream Apify changes
- [X] Containerize the app: Docker + Compose, `app` (Rails/Puma) + `db` (Postgres) services, isolated from ProPro's containers/DB
- [X] Health monitoring (see Section 5) — built with the Phase 4 orchestration below. `IngestionRunner`'s `ensure` block always saves the `IngestionRun` and calls both hermetic notifiers: `DiscordNotifier` posts the run summary to `#clubsync-log`, `HealthPing` pings healthchecks.io (`/start`, `/fail`, finish). Verified live in the September 2026 dry run (2 accounts: Discord summary + ping both confirmed). Remaining is only the operational setup on the E5440 at deploy time (crontab install). Full spec in `docs/HEALTH_MONITORING_PLAN.md`

**Phase 4 — Orchestration & resilience**
- [X] Build the `accounts` table (`Account` model, `db/seeds.rb` with the 41 handles) + `AccountPipeline` + `IngestionRunner` + the thin `clubsync:ingest` rake task — full spec in `docs/DATA_INGESTION_IMPLEMENTATION_PLAN.md`. `AccountPipeline` handles the per-account chain (fetch → `PostAdapter` → `PostLoader` → stage services) with narrow rescue on anticipated Apify failures; `IngestionRunner` loops `Account.all` sequentially so one account's failure doesn't abort the rest. This also landed Phase 1's health monitoring, which `IngestionRunner` calls out to (`IngestionRun` + notify/ping, see `docs/HEALTH_MONITORING_PLAN.md`)
- [X] Cron via the `whenever` gem, every 2 days — `config/schedule.rb` written and rendering verified. The actual host crontab entry (`docker compose exec app bin/rails clubsync:ingest`) gets installed on the E5440 at deploy time via `whenever --update-crontab`
- [X] Post state tracking: `stage` (`scraped → media_processed → extracted → deduped`, last completed stage; `deduped` terminal) + `is_event` (nullable boolean, set once extraction completes) + `last_error`/`stage_failed_at` for debugging. No backoff/retry-count mechanism — a stalled post (stage hasn't reached `deduped`) is simply re-attempted from its current stage the next time its account is scraped (every 2 days), since each stage's operation is treated as idempotent. `posts.last_ingestion_run_id` additionally ties each post to the run that last wrote it (health monitoring)
