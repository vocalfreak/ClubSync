# ClubSync Glossary

Terms as this project uses them.

- **Ingestion run / `IngestionRun`** — one pass of the `clubsync:ingest` rake task over the account list (every 2 days). The `ingestion_runs` table row is the single source of truth for what a run produced and what the Discord summary reports.
- **`is_event`** — nullable boolean column on `posts`, `nil` until a post reaches `extracted`, then derived once from the post's stored `category` via the `Categories` constant: the extraction LLM picks the category; the category→`is_event` mapping is pure code, no threshold. Independent of whether an `events` row exists (that table holds structured field data for confirmed events).
- **`csrw`** — a category in `Categories` (added 2026-09-24) for CSRW / Club & Society Registration Week content: the week's own invites, a club's "during CSRW" booth or lucky-draw promo, sign-ups for it, and the post-week thank-yous/recaps. Its stored value is the descriptive `club_and_society_registration_week` (the exact string the extraction LLM picks in the schema enum; `Categories::CSRW` is the constant). `event?("club_and_society_registration_week") == false`, so it never surfaces as an event card (yet it is technically attendable); posts keep their caption+images and stay queryable by `category`, which is what the future site's CSRW filter feeds on. Old pre-category posts are re-tagged by `CsrwRetagger` (`clubsync:retag_csrw`, lexical/fuzzy, no Gemini re-call). Agreed 2026-09-24 (pending build): new posts whose captions match the tightened `CsrwRetagger::MARKERS` (`\bCSRW\b` and the club-society form; the bare `registration|recruitment week` marker is dropped) are force-corrected *inside `Extractor`*, right after the LLM classification and before any `events` row is created — so a csrw post can never carry an event card and nothing is ever deleted in the live path; the one-off rake keeps its destroy semantics purely for repairing historical rows. Marker match wins even for a passing "after CSRW" mention — recall over precision, consistent with the recap-wins policy (pinned by a test).
- **Grace time** — healthchecks.io's "how late can the ping be" window past the 2-day period before the check is considered failed and `#clubsync-alerts` fires. Crashes don't wait it out — the app pings `/fail` immediately.
- **Hermetic notifier** — a reporting hook (`DiscordNotifier`, `HealthPing`) that rescues its own errors, logs them, and never raises. Control-plane failures never change run status and never suppress another notifier.
- **Dead-man's switch** — the healthchecks.io check acting as the external backstop for the app never getting to self-report (box down, OOM-kill, cron never fired).
- **Terminal stage / `deduped`** — the last pipeline stage (`scraped → media_processed → extracted → deduped`). A post that has reached `deduped` is "fully processed": post-loading skips it entirely on later runs and no stage re-runs for it. Not immune to future dedup: a `deduped` post stays eligible as a candidate against new same-account posts inside the rolling 0–21 day window, so a later run can still merge it and log a `deduplication` for it.
- **Candidate pair** — two same-account extracted posts that survive deterministic prefiltering (compatible `is_event` category, posted 0–21 days apart — the window admits both the same-day profile-grid series (several posts, one event, published together) and the spaced announcement→reminder pattern; the corroborated veto + date veto + `MAX_DATE_GAP` are what keep a same-day different-events pair separate), dates not implausibly far apart when both known, and get scored. Cross-account pairs are never candidates. Exception: a **near-simultaneous series** merges without scoring at all (see below).
- **Corroborated veto** — the dedup separate-verdict rule (decided 2026-09-24, build): a pair only vetoes on sub-floor caption when the art *also* disagrees — `caption Jaccard < 0.30` AND min Hamming `> 16` (`DHASH_STRONG_MATCH_THRESHOLD`) — and the `date` channel vetoes alone (structural). No single channel declares a pair different: identical art with a rewritten caption (the iem_mmu 17:46 trio from the 2026-09-24 A/B review: hash 0 + caption 0.10–0.18, which the old lone caption veto over-rejected) and an identical caption with barely-distinct art (Paw Fest) both resolve through the blend/ambiguity band, never a lone-channel veto.
- **Near-simultaneous series** — a candidate pair published within `SERIES_WINDOW_MINUTES = 30` of each other and not date-conflicting (both `starts_on` known *and* different) merges outright, bypassing scoring and vetoes — the mechanism that catches same-day promo bursts with distinct art or sub-floor captions (the MIMOS trio at 12:03–12:05, from the 2026-09-24 A/B review, was weak on every cheap channel and unreachable by the corroborated veto). Real bursts are 1–2 min apart, so 30 minutes is deliberate headroom (the review's original 30 was briefly tightened to 10 on 2026-09-24, then restored on 2026-09-25 so it stays comfortably above the observed bursts). The date guard is the scalability answer (a genuinely different event announced in the same hour stays separate); unknown dates still merge — a stricter "unknown → don't merge" variant structurally cannot catch the MIMOS trio, whose nil `starts_on` breaks its complete-link component. Such deduplications log `series: true` on `deduplications` (signal columns and `weighted_score` stay `NULL`, since nothing was scored) and remain subject to complete-link clustering.
- **Canonical event** — the `events` row in an event group that the public site's card shows, the group member whose post has the longest caption (the registration-style post with the most detail, chosen by that one simple tiebreak, wholesale — not a per-field cherry-pick, and not a confidence vote). Not a merge target: a post with no matches is a group of one, every `events` row in the group persists untouched, and the group's members stay linked via the shared `event_group_id` rather than being retired.
- **Deduplication** — one evaluated pairwise comparison between two same-account extracted posts, logged to `deduplications` (one row per pair): a pair-score audit log, never the mechanism that decides a merge itself, and never a review gate — every pair is acted on automatically (merge or stay separate) the moment it's scored. Corrective review after publication is a separate Phase 5 system, not a pipeline dependency.
- **`EventTags`** — the closed, frozen 37-value list of topical labels an event post can carry, stored on `events.tags` (a never-null string array, `[]` = untagged). A separate axis from `category`: non-exclusive (zero-or-more per event), informational only — no `event?`-style derivation, no confidence, no control flow, so it never surfaces as an event card or rejects anything. Values are the maintainer's display labels **verbatim** (Title Case, spaces and slashes intact — see the `docs/adr/` entry), because tags are what the future site filter shows, unlike the internal snake_case category enum. The extraction LLM picks from the same closed list in the schema; the parser drops any out-of-list value leniently rather than failing the post.
- **Transient Gemini failure** — Gemini's `TimeoutError` / `RateLimitedError` / `ServerError`, the only classes the extractor retries (3 attempts total, 2s then 4s backoff) and rotates across fallback models. `AuthError` is excluded — a config problem, not transient; this-post errors are never retried.
- **Dead-letter / `dead_lettered`** — a post whose tail of 3 most recent `extractions` rows are all `failed` with `error_kind: "this_post"`. The extractor then returns a skip: no Gemini call and no new `extractions` row, until a `succeeded` or `whole_service` row in that tail resets the streak. Counted on the run summary as a `dead_lettered` outcome under the `extracted` stage; `Post.dead_lettered` the scope exists for the (deferred) admin review view.
- **Payload preflight** — the size + decodability checks run before a Gemini round-trip: `GeminiClient` soft-warns at 12MB and hard-fails at 18MB on the serialized request body; the extractor rejects undecodable image bytes read from B2 locally instead of spending a wasted call.
- **Soft-cap alert** — a `#clubsync-alerts` alert fired when a run's daily Gemini usage crosses 80% of an env-configured cap (`GEMINI_DAILY_REQUESTS` and/or `GEMINI_DAILY_TOKENS`), counted from `extractions` rows. Inert until the real number is confirmed on the AI Studio dashboard and set.
